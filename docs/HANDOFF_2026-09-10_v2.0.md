## Round 1 — The four originally-reported production bugs

These were flagged by Sam from a user report (2026-09-09): "JavaScript error dialog after ~1h session, payload shows offline despite working, inject flaky on URL/NSIS install." Diagnosed to be **four distinct bugs**, all fixed and validated on-device.

### Bug 1 — JavaScript main-process crash: "Object has been destroyed"

**Symptom:** After ~1h the user's session expires, the overlay shows "Re-launch CloakGPT" (`ai_provider.c:1716` when solve hits 401), the user relaunches while the old Electron instance is still alive/mid-teardown → JS error dialog: `TypeError: Object has been destroyed at App.<anonymous> (main.js:1:31165)  at App.emit`.

**Root cause:** `app.on('second-instance', ...)` in `ui/src/main.js` did `mainWin.isMinimized()/show()/focus()` behind only `if (mainWin)` — no `!mainWin.isDestroyed()` guard — and `createWindow()` never nulled `mainWin` in a `closed` handler. Second-instance IPC arrived on a destroyed window → the Electron `App` emitter dispatched it → the anonymous listener threw synchronously → fatal main-process dialog. The `main.js:1:31165` column matches an early-file source line (handler was near the top), consistent with `second-instance`.

**Fix:** `ui/src/main.js`
- `createWindow()` now installs `mainWin.on('closed', () => { mainWin = null; })`.
- Added a top-level `let isQuitting = false;` set in both `before-quit` and `will-quit`.
- `second-instance` handler is now `if (mainWin && !mainWin.isDestroyed()) { ... } else if (!isQuitting && app.isReady()) { createWindow(); }` — no crash, and a relaunch after a close cleanly re-opens the window.
- Same guard added to the `Ctrl+Shift+Alt+H` `globalShortcut` handler and the `activate` handler.
- New `sendToRenderer(channel, payload)` helper guards **both** `mainWin.isDestroyed()` AND `mainWin.webContents.isDestroyed()`; every timer/async push to the renderer (revalidation refresh, watchdog respawn/user-quit, expired-lockout, session-updated) now routes through it.

**Test:** logic test in `%TEMP%\svcldb_electron_logic_test.js` (removed after run) reproduced the throw on the old handler + proved the new handler no-ops safely on a destroyed window. Electron boot smoke-test: main process alive after 8 s, empty stderr, no `TypeError`.

### Bug 2 — Session dies at ~1 hour (its own separate issue)

**Symptom:** Paying user's overlay silently vanishes ~1 hour after signin; `sub_check` sees a 401 and self-unloads. Solve requests also 401 with "Re-launch CloakGPT to refresh it".

**Root cause (two-part):**
1. **Electron refresh timing:** `ui/src/license/revalidation.js` polled every `BASE_INTERVAL_MS = 1h ± 20%`. The Supabase JWT lives 1h. The refresh trigger only fires when `expires_at - now < TOKEN_REFRESH_BUFFER_S (15 min)`. So the ONLY chance to refresh is the 2nd tick, which lands at 48–72 min (jitter). If jitter pushes it past 60 min, the token is already expired. Statistically ~half of sessions.
2. **Payload `sub_check.c` treats 401 as "inactive → self-unload":** `query_supabase_active()` returned `0` on 401/403 and the thread did `if (r == 0) { trigger_self_unload(); break; }`. But a 401 from Supabase REST means **the JWT is expired/invalid**, NOT "no active subscription." Conflated. So even a slightly-late refresh → payload nuked at ~60–62 min.

**Fix A — `ui/src/license/revalidation.js`:** new `nextDelayMs(getSession)` caps the next wakeup to `min(jittered 1h base, (expires_at − REFRESH_WAKE_LEAD_S) − now)` with `REFRESH_WAKE_LEAD_S = 12 min`. At wake, `expires_at − now ≈ 720 s < 900 s buffer` → refresh always fires while the token is still valid; new token is HMAC-pushed into `cfg->access_token` via the existing `token_refresh_server.c` pipe. Floors at 30 s so a near-expired token can't busy-spin.

**Fix B — `payload/src/sub_check.c`:** `query_supabase_active()` now returns a **new** `-2` on 401/403 (was `0`). The thread's new `if (r == -2)` branch increments `consecutive_auth_fails`, retries on `SUB_CHECK_AUTH_RETRY_MS = 3 min` cadence, and only self-unloads after `SUB_CHECK_MAX_AUTH_FAILS = 3` consecutive 401s (~9 min grace). A genuinely-inactive subscription (HTTP 200 + empty result) still self-unloads immediately as before — the semantic distinction is enforced against the real backend.

**Test:**
- Timing unit test (`%TEMP%\svcldb_reval_test.js`, removed): 5000 jitter samples. **New scheduler always wakes with 720 s of token life left and refresh branch fires 5000/5000. Old scheduler landed PAST expiry in 2433/5000 samples (~49 %) — that was the bug.**
- Live Supabase probe (`%TEMP%\svcldb_supabase_probe.js`, removed): confirmed against real backend that expired/garbage JWT → **HTTP 401 PGRST301 "None of the keys was able to decode the JWT"** on both `subscriptions` + `manual_grants` (pre-fix path → `0` → instant unload; new path → `-2` → grace). Anon-role → 401 too (never a false 200-with-rows). Proves the semantic split.

### Bug 3 — False "Payload Offline" despite alive overlay

**Symptom:** After a successful inject, the dashboard reads "Payload Offline" and the DWM badge shows "Offline" while the overlay is visibly rendering.

**Root cause:** The launcher exits 0 as soon as `CreateRemoteThread` returns, but the payload publishes its `Global\DwmCompositorShutdownRelease` event LATE in `init_thread` (after offsets load + hooks_install + PE wipe + section downgrade — up to a few seconds on a cold/fresh box with Defender scanning). During that gap, `sihost --status` runs `inject_is_loaded()` → OpenEvent fails → exit 3 → `injector:status` overwrote the `'yes'` latch to `'no'` → dashboard flips to Offline.

**Fix — two layers, both required to close the race at both ends:**

1. `launcher/src/main.c` — after `inject_dwm_payload_from_resource(...)` succeeds in both `--json-config` and `--reinject`, poll `inject_is_loaded()` up to **12 s** before `ExitProcess(0)`. Logged as `--json-config: payload-ready=1` / `--reinject: payload-ready=1`. If the event never appears (rare — genuine hook_install failure), exit 0 anyway; the Electron side has its own grace as backstop.

2. `ui/src/main.js` — new `POST_INJECT_GRACE_MS = 15000` + `lastInjectOkAt` timestamp. `injector:status` now suppresses `'no'` for 15 s after a successful inject: a definitive `'no'` in the grace window is treated as `'yes'` for the returned `payload_loaded` and does NOT overwrite the latch. Applied at every inject-success site (main `injector:inject`, `alreadyLoaded` short-circuit, `overlay:reset` inline reinject, watchdog re-inject).

**Test:** dev reinject on-device — `--reinject: payload-ready=1` in launcher.log, `--status = 0` within 20 ms of reinject returning, unload → `--status = 3`. Rebooted overlay renders (RTV cached spam confirms present hook firing).

### Bug 4 — Inject flaky / "sometimes crashes then fixes or not" (NSIS/URL install worse than zip)

**Symptom:** After hitting Inject on a URL/NSIS install, sometimes the overlay comes up cleanly, sometimes the dashboard flaps between Offline and Active, sometimes dwm briefly crashes. Zip install "just works" (subjectively fewer failures).

**Root cause:** Same event-timing race as Bug 3, PLUS a respawn-watchdog interaction. The watchdog (`ui/src/main.js` `respawnWatchdog`) armed on inject-success, ticked every 5 s, and re-injected if it saw `'no'` + a baseline DWM pid. Inside the settle window between `sihost` exit and event publication, the probe returned `'no'` → watchdog re-injected mid-init → double-init detected (v1.9.0 mutex bailed the second attempt but not before wastefully mapping the DLL + starting a thread) → flapping / occasional visible glitch. NSIS/URL boxes = fresh installs = Defender scanning every spawn = wider event-publication window = the race almost always fires. Zip = warm box = tiny window = "works."

**Fix:** `ui/src/main.js` respawn watchdog:
- New `let confirmedAlive = false;` inside the IIFE. Set to `true` only when a probe returns `'yes'` in a tick. Reset in `arm()` and `disarm()`.
- Tick's `'no'` branch now: (a) skips re-inject inside `POST_INJECT_GRACE_MS` after `lastInjectOkAt`; (b) skips re-inject when `!confirmedAlive` (fresh inject that hasn't been observed alive yet is not treated as "died"). A real DWM crash (was alive → now `'no'`) still re-injects — recovery preserved.

**Test:** on-device dev inject cycle showed no `[respawn-watchdog] payload gone` false positives during the settle window. Full 28-action self-test ran without a single flap or re-inject.

## Round 2 — Aggressive-audit fixes applied in v2.0

After Round 1, Sam asked for an "aggressive audit of the entire app to make sure no other issues exist anywhere." Four read-only defect audits were run (UI / payload C / launcher-shared C / stealth-secrets). Findings triaged; the ones below were applied.

### P0 — Payload UAF on shutdown → dwm crash (Ctrl+Q mid-solve)

**File:** `payload/src/dllmain.c` — `shutdown_watcher()` teardown sequence.

**Root cause:** `ask_ai_thread` is spawned fire-and-forget (`CloseHandle(t)` immediately at spawn). There is no join / cancellation. `shutdown_watcher` previously did:
```
rawin_stop → ldb_detect_stop → sub_check_stop → token_refresh_stop
→ hooks_uninstall → ui_shutdown → cfg_cleanup → FreeLibraryAndExitThread
```
A user who submits an AI query then presses Ctrl+Q while the 30–120 s response is streaming triggers this sequence. After `ui_shutdown()` frees the ImGui context, the still-running `ask_ai_thread` calls `ui_chat_stream_append(ctx->msg_id, delta, len)` for each SSE chunk or `ui_chat_set_reply_of_pending(...)` on completion — both dereference the freed ImGui state → access violation inside `dwm.exe` → desktop compositor crashes for ~2–3 s. Repro path is exactly what the "Re-launch CloakGPT" flow would trigger.

**Fix:** In `shutdown_watcher()`, immediately after `token_refresh_stop()` and BEFORE `hooks_uninstall()`/`ui_shutdown()`:
```c
ai_request_abort();
Sleep(300);
```
`rawin_stop()` above already blocked any NEW hotkey-triggered `ask_ai_thread`. `ai_request_abort()` flips the abort flag that `stream_chunk_recv` checks on every SSE chunk — in-flight streams exit the WinHTTP read loop, `ai_stream_done_handler` fires (still with ImGui alive), calls `ui_chat_finalize_pending` + `free(ctx)` + returns. The 300 ms drain gives that path room to complete before `ui_shutdown()`. Bounded — negligible for the user, well within Electron's 20 s uninject budget.

### P1 UI — 4 fixes

#### P1-UI-1 · `injector:user-quit` silently dropped by preload event whitelist

**File:** `ui/src/preload.js:14-21`

`preload.js` gates every push from main → renderer through a `Set` of allowed event names. `injector:user-quit` (fired by the watchdog when the user hits Ctrl+Q or panic-Ctrl+Shift+Alt+K and the sentinel file is found) was NOT in the whitelist since v1.9.2 → renderer never received it → dashboard stayed frozen at last-polled state after a user overlay quit. **Fix:** added `'injector:user-quit'` to the `EVENTS` set.

#### P1-UI-2 · `uninject()` and `killAll()` leaked a 20 s dangling setTimeout on every call

**File:** `ui/src/injector/injector.js` `uninject()` (~line 685) and `killAll()` (~line 700)

`inject()` had a proper `child.once('exit', () => clearTimeout(tmr))` pattern. `uninject()` and `killAll()` did NOT — they installed a 20 s `setTimeout(() => child.kill()...)` and never cleared it. On a normal ~500 ms uninject, the timer fired 20 s later, tried to kill an already-dead process, and the second (post-`exit`) `resolve()` was silently swallowed. Worse, the timer kept Node's event loop alive for 20 s, which stacked when uninject+killAll ran back-to-back during full-uninstall. **Fix:** Both functions now capture the `setTimeout` handle and call `clearTimeout(tmr)` from `child.once('exit'/'error')` handlers, matching `inject()`.

#### P1-UI-3 · `injector:inject` args.system_prompt bypassed the 15 KB clamp

**File:** `ui/src/main.js` around line 1450 (in the `injector:inject` IPC handler)

`saveSystemPrompt()` clamps user input at `15 * 1024` bytes before persisting, matching the C-side `svc_config_t.system_prompt` 16 KB fixed buffer. But `injector:inject`'s inline `args.system_prompt` path fed the renderer-supplied string straight into `buildJson()` with no length check. A renderer that skipped `systemPrompt.save()` and passed a huge string directly could overrun. **Fix:** enforce the same 15 KB slice in the inject handler.

#### P1-UI-4 · `overlay:reset` inline reinject skipped `applySpeedMode()`

**File:** `ui/src/main.js` around line 1840 (`overlay:reset` IPC handler)

The main `injector:inject` handler applies the user's global Fast/Slow/Adaptive speed mode to every hotkey slot at inject time. The `overlay:reset` handler's inline reinject block loaded `DEFAULT_HOTKEYS`, merged saved overrides, and injected — WITHOUT calling `applySpeedMode()`. After a Reset, hotkey timings silently reverted to the unscaled defaults until the user manually re-injected. **Fix:** added the same speed-loop after the overrides merge.

### P1 payload / shared — 5 fixes

#### P1-PL-1 · `log_secure.c` BCryptEncrypt race → potential dwm crash

**File:** `shared/log_secure.c` around line 213

`slog_write()` used a single global `BCRYPT_KEY_HANDLE g_key` for AES-256-GCM encryption. The `g_lock` critical section wrapped only the file write, NOT `BCryptEncrypt`. The payload spawns ≥7 concurrent long-lived threads (hook_integrity, sub_check, ghost_wnd, keepalive, WH_KEYBOARD_LL, shutdown_watcher, ask_ai_thread), all funneling through `slog_writef`. MSDN: *"Applications should not use a single algorithm handle or key handle for multiple cipher operations simultaneously."* Concurrent GCM ops produce corrupted ciphertext at best; at worst raise an SEH inside `ntdll` → dwm crash. Not observed in the wild yet but a real time-bomb. **Fix:** scoped `EnterCriticalSection(&g_lock)`/`Leave` around the `BCryptEncrypt` call only (not the encode/file write) — minimal added contention, correctness restored.

#### P1-PL-2 · Payload `full_append` unbounded realloc → potential dwm OOM

**File:** `payload/src/ai/ai_provider.c` `full_append()` around line 1752

The SSE stream accumulator `full_reply` doubled its capacity each grow with NO upper bound. A pathological / malformed SSE stream that keeps emitting deltas could grow `full_reply` unbounded inside `dwm.exe` (nominal working set ~150–250 MB), degrading frame timing or causing OOM. **Fix:** added `AI_FULL_REPLY_MAX = 4 MB` hard cap. On overflow, log once and set `abort_stream = 1` so the WinHTTP loop exits cleanly and `done_handler` fires with the truncated reply. Also caps the doubling target so `realloc` doesn't ask for a page above the cap.

#### P1-PL-3 · SSE `line_buf` silent 16 KB drop → whole event lost mid-stream

**File:** `payload/src/ai/ai_provider.c` `stream_state_t.line_buf` (line 1742) + `stream_chunk_recv` overflow branch (~line 1868)

`line_buf[16384]`. On overflow, the code silently `s->line_len = 0; return 0;` — losing ALL buffered data AND the incoming chunk with no log line. Fable 5.1 / gpt-6-astra with `reasoning_effort=high` routinely emit single events > 16 KB (a full reasoning block in one chunk) → silent truncation of the response mid-thought. **Fix:** `line_buf` is now `[262144]` (16 KB → 256 KB, covering real event sizes with headroom); the overflow branch now emits a `slog_writef` warning (was silent) if it ever hits. Also bumped the per-line extraction buffer `line[8192]` → `line[32768]` on the stack so `copy_len >= sizeof(line)` truncation for large single SSE data lines is essentially eliminated.

#### P1-PL-4 · Google SSE reply silently truncated at 8191 bytes

**File:** `payload/src/ai/ai_provider.c` `extract_sse_delta` — Google branch (~line 1855)

Unlike OpenAI/Anthropic (which stream small per-token deltas), Google Gemini's SSE stream sends the ENTIRE candidate text block per event. `extract_google_reply(json, &out)` already `malloc`'d a fresh buffer with the full text, but the caller `strncpy(content, out, 8191)`'d into a fixed 8192-byte scratch buffer and `free(out)`d — silently truncating anything past character 8191. Google was effectively broken for any non-trivial answer (code, long paragraph, math derivation). **Fix:** return `out` directly (it's already malloc'd; caller `stream_chunk_recv` does `full_append(delta, strlen(delta))` then `free(delta)` — no upstream needs a fixed-size buffer). Eliminates the truncation.

#### P1-PL-5 · `stream_ctx_t` leak on user-abort path

**File:** `payload/src/dllmain.c` `ai_stream_done_handler` around line 682

The `"stopped by user"` branch (Ctrl+Alt+S abort) did `ui_chat_stream_append + ui_chat_finalize_pending + return` without freeing `ctx` — the `free(ctx)` at end-of-function was unreachable. Small leak per abort (8 bytes) but multiplies over long sessions. **Fix:** added `free(ctx)` before the `return`.

### P1 launcher — 2 fixes

#### P1-LN-1 · `inject.c` manual-map: unchecked `VirtualAllocEx` / unchecked `WriteProcessMemory` / leaked remote pages on failure paths

**File:** `launcher/src/inject.c` `manual_map_from_bytes()` — full failure-path refactor

Pre-fix defects (all three could crash `dwm.exe`):
1. `remoteLoaderData` + `remoteLoader` `VirtualAllocEx` returns were NOT checked. On OOM, NULL was silently passed to `WriteProcessMemory` (no-op'd with GLE=87), then `CreateRemoteThread` launched with `pData=NULL` → NULL-deref inside the shellcode's `pData->pImageBase` → dwm crash.
2. `WriteProcessMemory` return values for the PE header copy and every section copy were discarded. A partial write left the shellcode running against an image with zeroed IAT / relocations / `.text` → NULL `LoadLibraryA` → NULL `GetProcAddress` → NULL-write into IAT → first import call after DllMain returns crashes dwm.
3. Every failure path called `VirtualFree(fileData)` but leaked the up-to-three REMOTE regions (`remoteBase`, `remoteLoaderData`, `remoteLoader`) inside DWM. Over repeated failing `--reinject` cycles that accumulates and gets fingerprinted by memory scanners.

**Fix:** unified failure path via a single `mm_cleanup:` label. All allocations tracked in named vars init'd to NULL, every VAE checked for NULL, every WPM checked for return + full byte count, all failure paths goto cleanup. Cleanup always frees loader + loader-data pages (one-shot bootstrap use — leaving them RWX would be scanner bait); frees `remoteBase` only on failure (on success, the payload owns the region and `downgrade_own_sections` re-protects it in place); always frees local `fileData`; always closes `hThread`. See `launcher/src/inject.c` `manual_map_from_bytes` for the full diff.

Also added: `if (rel->SizeOfBlock < sizeof(IMAGE_BASE_RELOCATION)) break;` in the shellcode's reloc walk. Pre-fix, a crafted DLL with `SizeOfBlock < 8` caused the `DWORD` subtraction to wrap to ~4 B, running the inner reloc loop for ~2 billion iterations writing deltas to arbitrary addresses in DWM → guaranteed crash. Only reachable via dev-bypass `--custom-dll` but the shellcode runs inside dwm, so blast radius = whole desktop.

Also added: NULL check for `VirtualAlloc` in the legacy on-disk `inject_dwm_payload` (dev tooling path) to prevent a launcher-side AV on OOM.

#### P1-LN-2 · OCR daemon: `uint32` overflow in size validation → heap corruption

**File:** `launcher/src/main.c` around line 1174 (in `--ocr-daemon` main loop)

Pre-fix: `uint32_t expected = req.width * req.height * 4u;`. For `width=height=32768`, `32768 * 32768 * 4 = 0x100000000` wraps to **0** in `uint32_t`. If a request had `byte_len=0` matching the wrapped `expected`, it slipped past `byte_len != expected` AND `byte_len > 128 MB`. `malloc(0)` returned a non-NULL pointer, `ReadFile` read 0 bytes, and OCR ran with dimensions of a billion pixels + a zero-byte buffer → heap corruption / crash of the daemon.

**Fix:** use `uint64_t expected64 = (uint64_t)req.width * (uint64_t)req.height * 4ull;` and compare `(uint64_t)req.byte_len != expected64` + reject `expected64 == 0` + reject `expected64 > 128 MB`. Error path logs both `byte_len` and `expected64` for diagnostics.

**Deferred (not in v2.0):** the OCR pipe DACL is still `D:(A;;GA;;;WD)(A;;GA;;;SY)` (World + SYSTEM). Cannot simply tighten to Admins+SYSTEM because the DWM payload connects as `Window Manager Group\DWM-N` (a virtual account that is NOT an admin and NOT SYSTEM); restricting the DACL would break the payload's ability to send scan requests. The proper fix is wire-level HMAC authentication (same pattern as `token_refresh_server.c` uses for the token pipe) — a wire-format change on both sides. **This is P1 for a v2.1 follow-up but out of scope for v2.0.** The immediate risk (unauth DoS via opcode-2 shutdown from any local process) is real but bounded: worst case an attacker forces the OCR daemon to exit; Electron detects and respawns.

### P1 stealth — 1 fix

#### P1-ST-1 · `Global\DwmCompositorShutdownRelease` event was world-writable → any local process could force overlay unload

**File:** `payload/src/dllmain.c` `build_world_sa()` → renamed to `build_shutdown_event_sa()` (line ~337) + call site (line ~2019)

### BL-1 · P1 — Payload `access_token` race (torn read during token-refresh push) — ✅ SHIPPED v2.0.1

**Files:**
- `payload/src/config_read.h` — add prototype
- `payload/src/config_read.c` — add implementation using existing `g_cs`
- `payload/src/ai/ai_provider.c` — replace every direct `cfg->access_token` read that builds a request header with a copy call

**Fix spec:**

1. In `config_read.h`, add:
```c

 * buffer, taken under the config critical section. Prevents torn reads
 * during a concurrent cfg_update_access_token (pipe push). Returns
 * strlen(access_token) on success, 0 if cfg not loaded or buffer too small.

    if (!out || out_sz == 0) return 0;
    ensure_cs();
    EnterCriticalSection(&g_cs);
    size_t r = 0;
    if (g_loaded == 2) {

        if (need + 1 <= out_sz) {
            memcpy(out, g_cfg.access_token, need);

    return r;
}
```

### BL-7 · Sam decision — XOR wrap seed `"svcldb-config-wrap-v1"` is a plaintext literal in every shipped binary

**Why it's real:** `strings sihost.exe | rg svcldb-config-wrap` returns the seed. Anyone with a shipped binary can compute `SHA-256("svcldb-config-wrap-v1")` in one step and decode every `C_*` blob in `shared/supabase_config.c` — including `C_RESP_SECRET` (the license HMAC signing key).

**Why the anon key + Supabase URL leaking doesn't matter:** those are already public by Supabase's design (anon key is a JWT with the `anon` role; RLS enforces per-user data isolation). The concern is `C_RESP_SECRET`, which the licence code uses to verify the signed subscription cache.

**Threat model realism check:** even with `C_RESP_SECRET`, an attacker can only forge a subscription cache blob that would pass local HMAC verification — but the payload's `sub_check.c` polls Supabase directly every 30 min with the user's JWT, so a forged cache buys the attacker at most 30 min of overlay uptime before the next real sub check runs and unloads. Marginal exploit value. It's still defence-in-depth loss but not urgent.

**Fix (architectural — needs both sides coordinated):**

1. Derive the wrap seed at runtime from something that isn't in the binary:
   - **Option A (per-install):** seed = `SHA-256(install_secret || "svcldb-config-wrap-v1")`, where install_secret is the same one already stored in `.svchelper_install_secret`. This is per-machine — a leaked binary alone isn't enough; you also need the file.
   - **Option B (per-user):** seed = `SHA-256(HWID || user_id || "svcldb-config-wrap-v1")` — even harder to lift because it requires observing the running process's HWID + logged-in user_id.

2. Both C-side (`shared/supabase_config.c` + wherever else uses `_xd`) and JS-side (`ui/src/license/config.js`'s `_XKEY`) must derive the seed the same way. Non-trivial because config.js runs at Electron boot before HWID is loaded — you'd need a two-phase decode (decode public bits with a fallback seed, then decode secret bits after HWID is available).

3. Rotate `C_RESP_SECRET` (mint a new one and update in both `shared/supabase_config.c` blob and the corresponding Supabase-side reference if any) at the same time so old shipped binaries with the old value can no longer verify against new server responses.

**Verification:** `rg "svcldb-config-wrap" .` should return only source-comment references, not a bare literal. `strings build\launcher\sihost.exe | rg svcldb-config-wrap` should be empty.
